# Prompt: extract a tool profile and demo snapshots

Paste this into Claude Code or Replit Agent at the root of each tool's repository. Run it once per tool.

---

You are documenting this tool for the SPURLABS website and product films. Read the whole codebase first. Do not change application behaviour. Write only to `spurlabs/` at the repository root.

## 1. Write `spurlabs/profile.json` and `spurlabs/PROFILE.md`

Fill every field from the code, not from assumptions. Where something is not in the code, write `"unknown"`; do not invent it.

- `tool_id`, `name`, `one_line_value` (what it changes for the user, in one sentence), `problem` (the problem it removes, in the user's words)
- `users`: roles that use it (for example owner's project director, cost engineer, scheduler, lender's engineer) and what each does with it
- `lifecycle_stages`: which of opportunity, concept, selection, definition, FID, contracting, execution, commissioning, operations, end of life, and what it does at each
- `inputs`: every input with its format and source (file types, APIs, databases, manual entry)
- `outputs`: every output, its format and who consumes it
- `features`: each capability, the screen or endpoint that exposes it, and its status (working, partial, planned)
- `methods`: the mathematics and AI actually implemented, named precisely and with file paths. For example: critical path method, Monte Carlo (iterations, distributions, correlation handling), reference class forecasting (distribution fit, percentiles), genetic algorithms (encoding, fitness, operators), parametric duration or cost models (variables, fitted how), optimization (objective, constraints), retrieval (vector store, BM25, re-ranking, citation method), language models (which model, which tasks; confirm whether any number is ever generated by a language model), computer vision (models, what is detected), IFC or 4D linking
- `data`: datasets, their size (rows, projects, documents, lessons), provenance and licensing
- `integrations`: P6, Microsoft Project, Excel, IFC, APIs, other SPURLABS tools it reads from or writes to
- `differentiation`: what this tool does that an incumbent (Primavera, Procore, nPlan, ALICE, Buildots, Document Crunch) does not, in two or three precise sentences
- `evidence`: any measured results (time saved, accuracy against outcomes, users, pilots), with the source file or log
- `limitations`: what does not work yet
- `tech_stack`: languages, frameworks, hosting

## 2. Load the demo case

Use the case data in `spurlabs/case.json` if it exists; otherwise create it with these two cases so every tool tells the same story:
- Case A, Mesa Ridge Energy Center: a 1.2 GW 2x1 H-class combined-cycle plant in Arizona with an air-cooled condenser; FID March 2027; base estimate $2.36B.
- Case B, Harbor Point AI Campus: a 300 MW data center campus with on-site gas turbines, battery storage and a 345 kV substation; FID June 2027.

Put the tool into a realistic state for Case A (and Case B where it applies): data loaded, analysis run, results visible.

## 3. Capture snapshots

Start the app and use Playwright to capture every meaningful screen at 1920 x 1080, in demo state, into `spurlabs/snapshots/NN-short-name.png`, in the order a user would see them. For each screen, record in `spurlabs/snapshots/index.json`: file, route, what is on screen, the action that leads to it, and the single most important number or result visible.

Also record one 20 to 40 second screen video of the main workflow as `spurlabs/snapshots/workflow.webm` if Playwright video recording is available.

## 4. Write the demo script

In `spurlabs/DEMO.md`, write the click path for a 30 to 45 second demonstration of the tool on Case A: each step, what the viewer sees, and the one sentence a narrator should say. End with the output that hands over to the next tool in the lifecycle.

## 5. Report

Print a summary: files written, any field marked unknown, and anything that did not run.
